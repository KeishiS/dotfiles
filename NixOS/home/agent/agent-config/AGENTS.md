# AGENTS.md

## コミュニケーション

- 日本語で対応する。
- 標準出力やファイルへ出力する日本語は自然で簡潔な表現を用いて、です・ます調に統一する。
- 日本語の文脈に合わない単語や言い回しを使わない。
- 文書の見出しや項目名、性質・対象・条件・責務などを列挙する箇条書きは体言止めとし、
  本文や手順および操作を説明する箇条書きは通常の文で記述する。
- 簡単な質問には簡潔に答え、必要性のない長い背景説明や過剰な箇条書きをしない。
- 研究に関する文章では仮定、定義、主張、考察を区別する。

## 文書の執筆

- 人間向け文書は、専門分野が異なる大学の学部生でも前から順に読める文章にする。
- 専門用語は必要に応じて使用する。ただし、初めて使う箇所で、その文脈に必要な意味、目的または具体的な動作を説明する。
- 既存文書の語彙や文体に不自然な点がある場合は踏襲せず、この節の主張を優先して適切な表現で記述する。
- 文書は概要から詳細へ進む構成とし、目的、前提、操作、設計上の理由を区別する。
- 抽象的な名詞だけで説明を終えず、何を対象とし、どのような状態または動作を指すのかを書く。
- 英語の技術用語を直訳した複合語は、一般的な日本語として意味が伝わる場合だけ使用する。
  伝わりにくい場合は、対象や動作を具体的に説明する。
- 識別子、APIの項目名、設定名、コマンド、コード上の型名は原綴りを保つ。それ以外の一般用語は
  自然な日本語を優先する。
- 文章の作成後に、説明のない専門用語、意味を推測しにくい熟語、直訳的な表現が残っていないか読み直す。

## 作業方針

- 作業を始める前に`CONTRIBUTING.md`の有無を確認し、存在する場合はその内容に従う。
- 原則として、プロジェクトの既存フォーマットと命名規則に従う。ただし、人間向け文書の語彙と
  文体については「文書の執筆」を優先し、不自然な既存表現を新しい文章へ引き継がない。
- コードを変更した後はそれに対応するドキュメントやテストを確認する。
- 変更後は関連する範囲の検証を実行する。
- 破壊的操作または外部へ影響する操作は事前に確認する。

## Git操作

- `git status`、`git diff`、`git log`などの読み取り操作は必要に応じて実行する。
- 可能な限り、独立した変更単位でコミットする。
- GitHub上の本リポジトリを指すリモート名は`upstream`とする。
- `main`への直接pushは禁止する。必ず目的が分かる作業ブランチを作成し、
  Pull Requestから`main`へマージする。
- ブランチ名には作業主体と目的が分かる名前を使用する。
- force pushやブランチ保護の回避を行わない。

## GitHub操作

- GitHubのPull Request、Issue、Actions、Releaseを操作するときは、原則として`gh`を使う。
- 外部操作の前に対象リポジトリ、ブランチ、Pull Requestを読み取り確認する。
- Pull Requestには変更目的、主な差分、実行した検証を記載する。
- 新しい作業内容はGitHub Issuesで管理する。

## サブエージェントとGit worktrees

- 単純な質問や、前の結果に依存する逐次作業にはサブエージェントを使用しない。
- 独立して実行できる担当範囲が明確な調査、検証、テスト、レビューにはサブエージェントを適切に使用する。
- エージェントがファイルを書き換える場合は、Git worktreeと作業ブランチを活用する。
- worktree作成前に、未コミット変更と既存worktreeを確認する。
- 親エージェントはサブエージェントの結果、差分、検証結果を確認し、統合と最終回答に責任を持つ。
